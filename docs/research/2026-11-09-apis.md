# Can a per-app install be zero-click? NetBird, Authentik, Caddy, the identity providers, Docker

- **Question**: can installing an app need zero clicks in any dashboard, through APIs and a token given once at
  first-time setup?
- **Checked**: 2026-11-09, against official docs, API references and source.
- **Outcome**:
  - [ADR 0004](../adr/0004-two-identity-providers-one-contract.md)
  - [ADR 0005](../adr/0005-two-meshes-tls-ends-at-home.md)
  - [ADR 0006](../adr/0006-an-edge-on-every-node.md)

Versions checked:

| Software | Version | Date | Source |
|---|---|---|---|
| NetBird | v0.82.0 | 2026-10-29 | [releases](https://github.com/netbirdio/netbird/releases) |
| Authentik | 2026.8.5 | – | [compose](https://docs.goauthentik.io/compose.yml) |
| Caddy | v2.11.9 | 2026-11-05 | [releases](https://github.com/caddyserver/caddy/releases) |
| Docker Compose | v5.7.0 | 2026-11-02 | [releases](https://github.com/docker/compose/releases) |

**Verdict**: every per-app step has a documented API. The risks:
- NetBird's reverse proxy is in beta, its plan availability isn't documented, and the shared cloud cluster has limits.
- TLS passthrough means our own edge needs certificates, so a DNS provider token is needed too.

## NetBird management API

**Authentication**
- `Authorization: Token <PAT>`. Service users are recommended for automation. The cloud allows 120 requests a minute,
  with bursts to 1,200 ([auth](https://docs.netbird.io/api/guides/authentication)).
- Service users are created with `POST /api/users` and `is_service_user`
  ([users](https://docs.netbird.io/api/resources/users)).
- Tokens are created with `POST /api/users/{id}/tokens` and last 1–365 days, so rotation must be automated
  ([tokens](https://docs.netbird.io/api/resources/tokens)).
- Self-hosted: `POST /api/setup` works while no account exists, and returns a PAT when the server has
  `NB_SETUP_PAT_ENABLED=true` ([instance](https://docs.netbird.io/api/resources/instance)).

**Groups, policies, setup keys, peers**
- Groups: `/api/groups` ([groups](https://docs.netbird.io/api/resources/groups)).
- Policies: `/api/policies`, where a rule's protocol is `all|tcp|udp|icmp|netbird-ssh` with ports or port ranges
  ([policies](https://docs.netbird.io/api/resources/policies),
  [spec](https://github.com/netbirdio/netbird/blob/main/shared/management/http/api/openapi.yml)).
- Setup keys: `/api/setup-keys`, one-off or reusable, with `auto_groups` and `ephemeral`
  ([keys](https://docs.netbird.io/api/resources/setup-keys)).
- Peers: `/api/peers` has no create; peers join with a setup key ([peers](https://docs.netbird.io/api/resources/peers)).

**DNS**
- Nameserver groups ([dns](https://docs.netbird.io/api/resources/dns)).
- Custom zones arrived in v0.63.0 (2026-01-16) ([forum](https://forum.netbird.io/t/netbird-v0-63-0-released/448)):
  `/api/dns/zones` and their records, of type A, AAAA or CNAME ([api](https://docs.netbird.io/api/resources/dns-zones),
  [guide](https://docs.netbird.io/manage/dns/custom-zones)).
- **Wildcard records** (`*.home.example`) can be created by API. Record names pass `IsValidDomain`
  ([record.go](https://github.com/netbirdio/netbird/blob/main/management/internals/modules/zones/records/record.go)),
  whose regex allows a leading `*.`
  ([validate.go](https://github.com/netbirdio/netbird/blob/main/shared/management/domain/validate.go)). Only zone
  domains and CNAME targets reject wildcards ([PR #5211](https://github.com/netbirdio/netbird/pull/5211)). Clients
  resolve wildcards since v0.64.0 ([PR #5125](https://github.com/netbirdio/netbird/pull/5125)).

**Reverse proxy ("Services")**
- **Endpoints**: `/api/reverse-proxies/services`, `/domains` and `/clusters`
  ([services](https://docs.netbird.io/api/resources/services)).
- **Service fields**
  ([spec](https://github.com/netbirdio/netbird/blob/main/shared/management/http/api/openapi.yml)):
  - `mode` is `http|tcp|udp|tls`, where `tls` is passthrough routed by SNI;
  - `listen_port`;
  - `targets[]`, whose type can be peer, host, domain, subnet or cluster;
  - `options.proxy_protocol` sends a PROXY v2 header to the backend.
- **Custom domains**: `POST /domains` plus a wildcard CNAME to the cluster, validated through `validation.<domain>`
  ([custom domains](https://docs.netbird.io/manage/reverse-proxy/custom-domains)).
- **Any peer can be a target**, so an app on a second node can be published
  ([docs](https://docs.netbird.io/manage/reverse-proxy)).
- **Listen ports**: TLS services need a chosen listen port, and arbitrary ports only on clusters that support custom
  ports ([docs](https://docs.netbird.io/manage/reverse-proxy)). Classic found 443 and 8443 unavailable for TLS
  services on the shared cluster in 2026-10.
- **Status**:
  - beta since v0.65 ([blog](https://netbird.io/knowledge-hub/reverse-proxy));
  - L4 modes and PROXY v2 since v0.67 ([L4](https://netbird.io/knowledge-hub/l4-proxy));
  - private (mesh-only) services are not on the shared cloud clusters
    ([private](https://www.netbird.io/knowledge-hub/netbird-only-private-services));
  - self-hosting the proxy puts Traefik in front
    ([migration](https://docs.netbird.io/selfhosted/migration/enable-reverse-proxy)).

**Libraries and licences**
- Official Go REST client, BSD-3, including `DNSZonesAPI` and `ReverseProxyServicesAPI`
  ([pkg](https://pkg.go.dev/github.com/netbirdio/netbird/shared/management/client/rest)).
- Embeddable client `client/embed`, BSD-3 ([embed](https://pkg.go.dev/github.com/netbirdio/netbird/client/embed)).
- Linux nodes: `netbird service install`, then `netbird up --setup-key`
  ([linux](https://docs.netbird.io/get-started/install/linux)).
- `management/`, `signal/`, `relay/` and `proxy/` are AGPLv3, the rest BSD-3
  ([LICENSE](https://github.com/netbirdio/netbird/blob/main/LICENSE),
  [proxy](https://github.com/netbirdio/netbird/blob/main/proxy/LICENSE)).
- Mobile: the Android app accepts a setup key, and on iOS an MDM can supply one
  ([android](https://docs.netbird.io/get-started/install/android),
  [iOS MDM](https://docs.netbird.io/manage/peers/mdm-deployment/ios-mdm-policy)).

## Authentik (2026.8)

- **Tokens**: API tokens as Bearer ([auth](https://api.goauthentik.io/authentication/)). `AUTHENTIK_BOOTSTRAP_TOKEN`
  creates an admin token on first start ([automated install](https://docs.goauthentik.io/install-config/automated-install/)).
  Official Go client `goauthentik.io/api/v3` ([clients](https://api.goauthentik.io/clients/)).
- **One call per app**: `PUT /api/v3/core/transactional/applications/` takes the app, the provider model and provider,
  and its policy bindings ([ref](https://api.goauthentik.io/reference/core-transactional-applications-update)). The
  provider model can be `oauth2provider`, `proxyprovider` or `ldapprovider`
  ([enum](https://docs.rs/crate/authentik-client/latest/source/docs/ProviderModelEnum.md)).
- **Blueprints by API**: create, then apply ([ManagedApi](https://cdn.jsdelivr.net/npm/@goauthentik/api@2026.2.3-rc1/docs/ManagedApi.md)).
- **Forward-auth**: proxy providers in `forward_single` or `forward_domain` mode
  ([enum](https://docs.rs/crate/authentik-client/latest/source/docs/ProxyMode.md)), attached to the embedded outpost by
  PATCHing its provider list ([OutpostsApi](https://cdn.jsdelivr.net/npm/@goauthentik/api/docs/OutpostsApi.md)). The
  Caddy endpoint is `/outpost.goauthentik.io/auth/caddy`
  ([caddy](https://docs.goauthentik.io/add-secure-apps/providers/proxy/server_caddy/)).
- **LDAP**: an LDAP provider plus an outpost, which Authentik starts itself through its Docker integration
  ([outposts](https://docs.goauthentik.io/add-secure-apps/outposts/)).
- **Footprint**: 2 cores and 2 GB RAM minimum
  ([requirements](https://docs.goauthentik.io/install-config/install/docker-compose/)). Postgres plus server plus
  worker, no Redis since 2025.10 ([2025.10](https://docs.goauthentik.io/releases/2025.10/)). Outposts must run the
  server's version ([2026.8](https://docs.goauthentik.io/releases/2026.8)).

## Caddy

- **Admin API**: `/load`, `/config/<path>` and `/id/<id>`, with ETags ([api](https://caddyserver.com/docs/api)).
  Autosave, plus `--resume` to start from it ([cli](https://caddyserver.com/docs/command-line)).
- **forward_auth** is a Caddyfile shortcut for `reverse_proxy` with handlers; in JSON, write the handlers out
  ([docs](https://caddyserver.com/docs/caddyfile/directives/forward_auth)).
- **PROXY protocol**: a listener wrapper in core since v2.7
  ([module](https://github.com/caddyserver/caddy/blob/master/modules/caddyhttp/proxyprotocol/module.go)).
- **DNS providers**: more than 80 through libdns ([libdns](https://github.com/libdns/libdns),
  [caddy-dns](https://github.com/caddy-dns)), compiled in at build time
  ([architecture](https://caddyserver.com/docs/architecture), [build](https://caddyserver.com/docs/build)).
- **Embedding** Caddy in a Go program works, but the intended pattern is the other way round: your code as Caddy
  modules ([forum](https://caddy.community/t/example-of-go-embed-in-v2/6683)).

## Identity providers compared

- **Kanidm** v1.12.0, MPL-2.0 ([repo](https://github.com/kanidm/kanidm)):
  - OIDC, passkeys, read-only LDAPS and RADIUS.
  - OAuth2 clients by REST (`POST /v1/oauth2/_basic`)
    ([source](https://github.com/kanidm/kanidm/blob/master/server/core/src/https/v1_oauth2.rs)), with service-account
    tokens ([docs](https://kanidm.github.io/kanidm/master/accounts/service_accounts.html)).
  - No forward-auth; oauth2-proxy is the documented answer
    ([examples](https://kanidm.github.io/kanidm/stable/integrations/oauth2/examples.html)).
- **Pocket ID** v2.19.2, BSD-2 ([repo](https://github.com/pocket-id/pocket-id)):
  - passkey-only OIDC with a REST API ([api](https://pocket-id.org/docs/api));
  - no forward-auth ([proxies](https://pocket-id.org/docs/guides/proxy-services));
  - LDAP sync in only ([ldap](https://pocket-id.org/docs/configuration/ldap)).
- **Authelia** v4.39.28, Apache-2.0 ([repo](https://github.com/authelia/authelia)):
  - forward-auth and certified OIDC;
  - OIDC clients only in its config file
    ([clients](https://www.authelia.com/configuration/identity-providers/openid-connect/clients/));
  - a passkey counts as one factor ([webauthn](https://www.authelia.com/configuration/second-factor/webauthn/)).
- **Zitadel** v4.20.2, AGPL-3.0 since v3 ([blog](https://zitadel.com/blog/apache-to-agpl)):
  - full APIs;
  - LDAP only as an upstream source ([ldap](https://zitadel.com/docs/guides/integrate/identity-providers/ldap));
  - forward-auth through oauth2-proxy ([docs](https://zitadel.com/docs/examples/identity-proxy/oauth2-proxy)).

## Docker on several machines, and the Compose SDK

- **Remote engines**: contexts ([docs](https://docs.docker.com/engine/manage-resources/contexts/)), and SSH or mTLS
  ([docs](https://docs.docker.com/engine/security/protect-access/)).
- **How others do it**:
  - Portainer: an agent ([docs](https://docs.portainer.io/admin/environments/add/docker/agent));
  - Coolify: SSH ([docs](https://coolify.io/docs/core/how-coolify-works));
  - Dokploy: SSH or Swarm ([docs](https://docs.dokploy.com/docs/core/deployment-options)).
- **compose-go** is the reference loader ([repo](https://github.com/compose-spec/compose-go)).
- **The Compose SDK** is official since Compose v5.0.0 ("Compose can now officially be used as a SDK")
  ([v5.0.0](https://github.com/docker/compose/releases/tag/v5.0.0), [sdk](https://docs.docker.com/compose/compose-sdk/)).
  - It needs a pinned `docker/cli`.
  - It can drive a remote engine.
  - v5.7.0 changed library APIs in a minor release, so pin it.
