# Secrets as systemd credentials, sealed by the agent

App secrets are generated by HomersLab and stored as systemd credentials, a standard mechanism that keeps working
without HomersLab. The details come from the
[systemd credentials spike](../research/2026-11-09-spike-systemd-creds.md):

- **Sealing.** The agent, as root, seals each credential with an explicit `host+tpm2` key, or the host key alone where
  there's no TPM. It never relies on `auto`, for two reasons:
  - on a machine that boots in legacy BIOS mode, systemd reports no firmware TPM support and quietly uses the host key
    alone;
  - an unprivileged user can't ask for the TPM at all.
- **Delivery.** The app's systemd unit decrypts its credentials when it starts. It hands them to the containers as
  read-only files, through `--mount` or Compose `secrets:` only.
- **SELinux.** Each app gets its own SELinux MCS level. The unit relabels its credential files to `container_file_t` at
  that level, so only that app's containers can read them.
- **Ownership and names.** Each app declares the UID that reads its secrets. The name inside a credential equals the
  unit's credential ID.
- **Who can decrypt.** Root and the app's own unit. Nothing of HomersLab sits in that path.
- **Moving.** No sealed credential survives new hardware, a reinstall or a recreated user. The weekly archive carries
  the secrets in plaintext inside age, and a restore seals them again.

## Considered options

- **An encrypted store in the manager's database, with a TPM-sealed key.** An earlier answer in the grilling, replaced
  by this one.
- **Plain files readable only by root.** Anyone with a copy of the disk would have them.

## Consequences

- systemd owns the containers, so the engines' restart policies are not used.
- **Still to test as root, in a VM:**
  - system units;
  - rootful Podman;
  - sealing as root;
  - relabelling a system unit's credentials;
  - moves between machines.

## Amended (2026-11-11)

"The weekly archive carries the secrets" now means the archive that also runs after every change to a secret
([ADR 0010](0010-backups-restic-and-a-write-only-archive.md), amended; #88), so a secret made since the last weekly run
isn't lost with the TPM. A cleared TPM (a firmware update, a dual-boot "Clear TPM", a new motherboard) is a likely
event, so:
- at boot, a credential that fails to decrypt is reported once, as "this machine's TPM no longer opens HomersLab's
  secrets", with the restore-from-archive command, instead of a dozen failing units;
- a restore plan says when an app's secrets in the archive are older than its data.
